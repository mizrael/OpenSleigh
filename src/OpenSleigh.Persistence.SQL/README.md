# OpenSleigh.Persistence.SQL

# This package should not be used directly, unless you are intentionally using it to create a new SQL persistence layer. 

The following providers are already available:
- SQL Server: ![Nuget](https://img.shields.io/nuget/v/OpenSleigh.Persistence.SQLServer?style=plastic)
- PostgreSQL: ![Nuget](https://img.shields.io/nuget/v/OpenSleigh.Persistence.PostgreSQL?style=plastic)

## Notes for a new provider

- Register the context with `services.AddPooledSagaDbContext(builder => ...)`. Every consumer still gets a `SagaDbContext` of its own, but contexts are reused once disposed instead of being built for every message.
- `SqlOutboxRepository` implements `IOutboxBatchRepository`, so the outbox relay deletes what it published in a pass with one round trip: one statement by default, which a provider can replace by overriding `DeleteBatchAsync` (SQL Server deletes by key). The relay reads, publishes and deletes inside one transaction, on the context of `SqlTransactionManager`: pass it to the repository as `relayDbContext`.
- An outbox row has a due time, `DeliverAt`, when its message was published with a delay, and none otherwise. `ReadPendingQuery` is the statement a provider reads the outbox with: it must return the delayed rows that are due and the rows without a due time, each kind having its share of a pass so that neither keeps the other waiting, and it should find both through the index on the column (`OutboxMessage.DeliverAtIndexName`), so that rows that are not due cost nothing. A provider written for an earlier version overrode `ReadPendingAsync`: it now has to supply `ReadPendingQuery`.
- The outbox table has a nullable `FirstReturnedAt` column next to `DeliverAt`, on the entity every provider shares: **the schema upgrade of a provider has to add it**, or every insert into the outbox and every read of it fails, with any transport. This is a breaking change for a provider written for an earlier version.
- Taking back the messages a transport returned is optional, and only the RabbitMQ transport asks for it; a provider that does not loses the messages a RabbitMQ broker returns. One that does implements `IOutboxReturnRepository` on its repository and registers it as such. `PutBackAsync(command, message, cancellationToken)` of the base class runs the provider's command for one message, with the parameters `{0}` message id, `{1}` correlation id, `{2}` body, `{3}` message type, `{4}` creation time, `{5}` sender id, `{6}` due time, `{7}` time of first return. The command updates the row when it is there (the new due time, and the earlier of the two times of first return, a stored one earlier than the creation time not counting) and inserts it when it is not, waiting for a row a relay holds, and not for the rows next to it. It may fail when another host inserts the same message at the same moment, as the command of SQL Server does with a duplicate key: the transport tries again. The application needs the right to update the outbox table, which earlier versions did not. `ReadPendingQuery` has to lock the rows it returns, not only index entries, so that the command waits for the relay instead of deadlocking with it.
- A database created by a version before the `DeliverAt` column needs it added. Derive from `SagaDbSchemaUpgrade`: it lists the changes (`SagaDbSchemaChange`: a query that tells whether the change is applied, and the statements that apply it), and makes concurrent upgrades wait for each other in `RunExclusively(DatabaseFacade, Action)` (override the one that takes a change as well to open the transaction the change runs in). Register it with `AddSagaDbSchemaInitialization<TUpgrade>()`: the database is created or upgraded when the host starts, or with the first context when there is no host.
- Instances that start together on a database that does not exist, or has no tables, each try to create it. `RunExclusively(DatabaseFacade, Action)` of `SagaDbSchemaUpgrade` makes them wait for each other, for the creation of the tables and for every change of an upgrade, with a lock held by the connection (the tables are created in a transaction of their own). Creating the database itself cannot be waited for with a lock inside it: override `RunDatabaseCreationExclusively` when the server has another place to take one (the providers use its system database, and fail to start when they cannot take the lock there). Without it, all but one of the instances that start together on a server that does not have the database fail to start.
- A context configured with `UseSeeding` is seeded once the tables are there, and current: after their creation, or after the upgrade of the ones that existed. Either way it is seeded inside `RunExclusively`, so instances that start together seed one at a time; a context without seeding takes no lock when its tables are there. The seeding runs in a transaction. A context configured with `UseAsyncSeeding` alone fails to start, as it does with `EnsureCreated`.
- The providers take the lock for the creation of the database on the connection EF Core creates it with (`CreateMasterConnection` on SQL Server, `CreateAdminConnection` on PostgreSQL, which honours `UseAdminDatabase`): connection interceptors and authentication callbacks apply to it as they do to the creation itself. The creation runs with the command timeout of the upgrade on SQL Server; on PostgreSQL the provider creates the database with the timeout the context was configured with, and the administration database must not be the template of the new one (the start fails saying so).
